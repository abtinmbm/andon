### 2026-11-27: H7's unseen fault: a smaller tape piece, and how d4 is scored (Phase H7)
- **Tried:** session B's tape series first used d1's 12/6 × 6 mm trapezoid. In trial 1 it rubbed the frame: it sounded wrong, and the board's scores reached 15,173 against a calibration centre of 160.87, a contact fault rather than an imbalance. The run was stopped and voided after that trial, before any row was logged; the capture is kept outside the repo, not cited for figures. The tape was refitted as a 5 × 7 mm rectangle in the middle of one blade, clear of the frame, and that piece stayed on through the 10 trials and the d4 tape take (`configs/h2_recording.yaml`, `docs/recording_protocol.md`). The d4 scorer was then written before any d4 clip was scored: `andon.unseen` with `configs/h7_unseen.yaml` and `configs/h7_unseen_levelmatched.yaml`.
- **Result (scored once, `results/h7_unseen.md`, seeds 0-2):** as recorded (`h7_unseen`): AUC 100.00 ± 0.00, pAUC 100.00 ± 0.00, 100.00 ± 0.00 % of tape windows detected at 0.62 % false alarms reached (1 % target; 162 tape and 162 control windows, 18 clips each). At matched volume (`h7_unseen_levelmatched`): AUC 100.00 ± 0.00, pAUC 100.00 ± 0.00, but only 1.23 ± 0.00 % of tape windows detected at 0.62 % false alarms. Live on the board, the same tape was caught in 10 of 10 trials (`h7_imbalance_large`). Read from a recompute of seed 0, not logged: the tape take is 2.67 dB louder than the control take. At matched volume the control windows' median score is 157.3 and the tape windows' 650.1, but a few control windows score far higher (up to 1338.0). The 1 % threshold allows one of the 162 control windows above it, so it lands at 1312.2823 (seed 0), above nearly every tape window.
- **Decision:** reported as is; nothing is tuned on it. The choices below were fixed before scoring:
  - The model is `h3_gmm` unchanged, trained on every usable normal clip of d1 and d2 (the eval fold's training set), seeds 0-2.
  - d4 has no main normal take, only the control take recorded after the tape take (tape off, fan lifted and put back). So the 18 tape clips are judged against those 18 control clips: clip AUC and pAUC.
  - Detection at 1 % false alarms is per window: the share of tape windows above the lowest threshold that at most 1 % of control windows exceed. With about 150 control windows, that threshold allows one control window above it.
  - The level-matched config shifts every d4 window to the control take's mean level (`match_levels` with the control take as reference; d4 has no limit clips), since a remount alone moves the level (2026-11-20).
- **Why:** the trapezoid rubbing the frame would have measured a different fault. A smaller piece risks a fault too weak to see (d1's 5 × 5 mm square changed the 0-125 Hz band by only +0.5 dB), but it was fitted before any tape trial was kept and nothing was chosen on it. The control take is the only normal running in d4, so it is the only fair comparison. The two configs together say whether the model hears more than a change of level. They say: averaged over a clip, the shape alone separates the tape from the control take; window by window at matched volume, a few control windows score higher than the tape (inferred cause, not tested: shifting a quiet or loud window by its whole level gap pushes it far from the training spectra). So the window figure at matched volume is set by those few control windows, out of 162.

### 2026-11-27: Silent wrong answers become errors: NaN metrics, truncated WAVs, duplicate labels, partial H3 folds (all phases)
- **Tried:** the second external review's cheaper correctness findings, checked against the code; no run, no result changes. (1) `andon.reproduce` took the largest AUC/pAUC difference with `max()`, which skips a NaN, so a NaN metric read as "Reproduced". (2) `read_wav` read whatever bytes a file held, so a truncated WAV was a shorter clip. (3) A file listed twice in the DCASE labels kept its last label. (4) The Python light accepted a NaN score (it compares False, so it counted as low and could clear a yellow) and limits with no spread; the board trips red or refuses both (`andon_light.c`, `detector.c`). (5) The int32 guards used `abs()`, so they missed NaN and refused the valid minimum. (6) An int8 GMM whose precision Cholesky diagonal rounds to 0 gave NaN scores. (7) `budget.module_macs` left a training model in eval mode. (8) H3 did not refuse a session listed as both dev and eval, or a fold tested on a session it trains on. (9) H3's resume skipped a (fold, seed) with any logged row, so a run cut off part-way passed as finished.
- **Result:** each fix has a test that fails on the code before it (13 new tests). Every logged H3 set is complete (30 scoring sets of 9 rows, 24 light sets of 3), so a rerun of a logged config still skips instead of refusing; the shipped split has no overlapping session.
- **Decision:** kept. Each case now raises, or is a failed check, instead of giving a number. A partly logged H3 fold is refused rather than completed, because log rows are never edited by hand.
- **Why:** each was a way to get a plausible result from bad input without notice. Left as documented limitations: the feature cache is keyed by clip names, not contents (no logged result depends on a changed file; a fix would mean recomputing every cache), the downloader checks the archive hash but not the extracted file list, and three small Stage 1 cleanups that would touch code `andon.reproduce` guards.

### 2026-11-27: "Fan off" is proved by the board's state, not by duty 0; H7 logs only complete captures of the right model (Phase H7)
- **Tried:** fixes after a second external review, before the H7 rerun; no board run, no result changes, no reflash. (1) Cleanup trusted the last ack's duty. While red the board's duty is 0 anyway, so a `fan off` lost on the line still read as confirmed, and the button that clears red restarts a fan still asked on (`main.c`). (2) A command was logged before it was written, so a capture file that failed to write stopped a cleanup's `fan off` from being sent; cleanup caught only the tools' own error. (3) H7's "fit the fault" prompts, and the recorder's last `fan off`, did not check the ack at all. (4) `jidoka run` and `fan_latency` left on a red light without sending `fan off`, `fan_latency --listen` never sent it, and the recorder's `fan speed` was outside its cleanup. (5) `andon.h7 report --log` logged a series with fewer trials than planned, or a short soak, into the once-only row. A trial without its opening status line counted windows from the board's lifetime total. A replayed older cut could time a stop before its trip. Neither the H6 nor the H7 tool checked which model the board says it runs. (6) The report's `--out` could overwrite its own capture, an absolute wildcard failed on Windows, and a closing limits line turned the stopped dashboard back to watching. (7) The recorder accepted a take too short for one clip (and a zero clip length) after starting the fan, did not create WAV files exclusively, and kept newline-free noise without bound.
- **Result:** each fix has a test that fails on the code before it (21 of the new tests). Every `fan off` ack in the 11-27 board captures (build `7670489`) passes the new check, and they parse to the same trials as before.
- **Decision:** kept. An ack proves the fan off only if it was accepted, shows duty 0, the gate pin read back low, and `want_on=0` (`jidoka.is_off`). Cleanup writes before it logs and goes on through any error. H7 asks for hands in the fan, or for the button, only after such an ack; otherwise it stops and says to unplug the fan. The tools refuse a board whose build line names another model, and `report --log` refuses any capture with a problem the parser found. Trips and cuts stamped before the start (or before the trip) are not taken as evidence.
- **Why:** H7 session B asks a person to reach into the fan between trials, and its rows are logged once. Two findings were not fixed: two runs appending to the results log at the same moment (never done here), and the feature cache keyed on file names only. The fan recordings are never overwritten, each H3 fold caches under its own name, and the DCASE files are hash-checked, so no logged result depends on it. Fixing it would invalidate every cache.

### 2026-11-25: Bench tools turn the fan off first and never overwrite a capture; non-finite scores are refused (Phase H7)
- **Tried:** fixes after an external code review, before the H7 board sessions; no board run, no result changes. (1) `andon.h7 series` counted windows to red from zero, so a fit-once trial (the tape fault) reported the board's lifetime window count: 6, 9 and 12 on the scripted board where each trial took 3. (2) The H6 and H7 cleanup sent `fan speed` before `fan off`, so a lost ack on the first skipped the second; `andon.record` sent `fan on` outside its cleanup block, and `andon.fan_latency` had none. (3) H6 and H7 opened the output file before the serial port, so a busy or mistyped port emptied an existing capture. (4) `roc_curve` accepted NaN scores: every NaN forms its own threshold, so an all-NaN vector with positives first scored AUC 1.0.
- **Result:** every logged row has finite scores and no committed capture is affected (the H6 captures are single trials; H7 has none yet). Each fix has a test that fails on the old code.
- **Decision:** kept. (1) Each trial counts from the window count on the status line that opens it. (2) Cleanup sends `fan off` first and tries every command even if one before it got no ack; "remove the fault" is printed only once an ack shows duty 0, otherwise the tool says to unplug the fan. `record` and `fan_latency` always end with `fan off`. (3) The port opens first and the capture is created exclusively: an existing file is refused, never overwritten. (4) Non-finite scores raise.
- **Why:** H7 reports windows to red for the tape trials, and asks a person to reach into the fan after a series; both have to be right before session B. Firmware findings from the same review (the reset button accepting a press that began before red, the mic ring check timing from the last call instead of the last catch-up, light run counts kept across an audio restart, the on-board self-test losing a NaN) need a reflash, so they wait until H7 is done: H7 measures one fixed build.

### 2026-11-22: H7's live trials: one fan, one calibration, three ways to start a fault (Phase H7)
- **Tried:** the measurement design and its tool, before any board run. `andon.h7 soak` (`configs/h7_soak.yaml`) counts every stop over 60 minutes of watched normal running. `andon.h7 series` runs 10 trials per fault on the limits already on the board: `h7_underspeed` (a serial switch to 85 %), `h7_obstruction` (the card strip fitted by hand with the fan off, then `fan on`, every trial) and `h7_imbalance_large` (H7's unseen fault, the tape fitted once, then 10 restarts). Each switch or card trial first runs 30 s watched with nothing changed, and a stop there is counted as a false stop. The firmware's `status` now also prints the limits, so every capture holds the limits it is judged against. The recorder refuses a take while the board watches a fan (`--unwatch` sends `watch none`). The tape takes go in a new `unseen` session, `d4`, under `unseen_faults`, so no H3 fold, training set or guided session can use them.
- **Result:** none yet (tool and tests only).
- **Decision:** kept, with these choices (2026-11-22):
  - Everything runs on `id_00`: H6's slowest stop (11.661 s) and the fan with the unseen fault. Three fans would take three calibrations and about three times the board time.
  - One calibration for the session. A stop and restart keep the board's limits, which is how the system runs once deployed; a fresh 10-minute calibration per trial would also make 30 trials take about 6 h.

  - A card or tape trial is timed from `fan on`, a command on the board's clock, so its time includes the 5 s hold-off and the kick-start. A key press when a fault is fitted by hand is not on the board's clock.
  - The tape is fitted once: re-taping changed the fault from take to take in d1, which is why imbalance was retired then.
- **Why:** each choice keeps the measurement on the board's own clock and makes it a single, unchosen run of the final system. What the numbers will not cover: other fans, other rooms (planned as a later, separate block), or a tape fault that appears while the fan runs.

### 2026-11-19: The on-board detector: stream framing, calibration on the device, and fail-safe stops (Phase H6)
- **Tried:** a plain-C detector (`firmware/src/detector.c`). It turns the mic's 256-sample chunks into 1024-sample frames every 512 samples, then runs the C log-mel, the GMM window and the watched fan's score, and feeds the result to the light (`firmware/src/andon_light.c`, a port of `andon/light.py`). Its settings are exported into `andon_gmm.h` from `h2_recording.yaml` and `h3_gmm.yaml` (gain shift 4, hold-off 80,000 samples, 584 calibration windows, light 2/3/3), not written by hand.
- **Result:** in the host tests, the exported real-mic test audio, fed in 256-sample chunks, gives the scores Python gives for the board's windows to 6.52e-06 relative (tolerance 1e-04). The C light's limits match `andon.light` to 1.93e-16, and its light differs on 0 of 25 test states. CI run 44663730659 was green on `55cd2cf`.
- **Decision:** kept, with these choices (2026-11-19):
  - The board frames without padding, so its frame t is Python's centred frame t + 1, and its windows sit one frame later than H3's. The test vectors score the board's own windows.
  - The limits are fitted on the device and kept in RAM, refitted after a reboot, a `watch` or a `calibrate`. H3 showed that a remount needs new limits, and flash storage would risk stale ones.
  - `watch <id>` is required before anything is checked. A default fan would quietly score with the wrong fan's model.
  - The board stops the fan when it can't hear: no mic words for 250 ms, or about 1 s of flat signal. A watchdog (1 s) reboots a hung loop, and the board then comes back red with the fan off.
  - The button only clears red; it no longer steps the light (that was H0's test mode).
  - Text output is written only when the USB buffer has room, and dropped and counted otherwise. A blocking printf (up to 500 ms) would starve the 256 ms mic ring and trip the watchdog.
- **After the review (not on the board yet):**
  - A new hold-off (after `watch`, `calibrate`, or a stop and restart) now clears the light's run counts and a yellow light; red stays latched. Before this, two windows above the old limit carried over, so a single window above the new one would turn red. It didn't affect the trials: the board had scored no windows before each `watch`. The fix needs a reflash before H7.
  - `andon.jidoka` now fails a trial whose switch is made with the light off green or not at the fault duty, or whose audio stream restarted. It logs `nan`, not a negative time, for a trial that never stopped, and refuses two trials of one fan in one batch. The closing status's detector line is now captured. The H6 captures predate this, so their restart counts read as not captured.
  - The live page is a new page that reads the capture file. It is not the Stage 1 dashboard; the board's scores reach it over USB serial through the tool.
- **Why:** each choice either keeps the board's numbers comparable to H3's (the same front end, model, limits rule and light) or makes a failure stop the machine rather than leave it running unwatched.

### 2026-11-19: The per-fan GMM ported to C in float32, checked on the board against Python (Phase H5)
- **Tried:** H5 ports H3's final model instead of the Stage 1 CNN (2026-11-18). `andon.export_gmm` refits `h3_gmm` on d1+d2 with seed 0, the model scored once on d3, through the same clips and code as `h3.score` (`h3.training_clips`, factored out of `fold_clips`); it reads no d3 audio. Its test vectors are each fan's first d1 clip (4.06 s, 3 windows), so they also check the C front end on the real microphone's audio, and every window is scored by all three fans' GMMs. The C scorer (`firmware/src/gmm.c`) keeps the window mean as two half-window sums and computes the full-covariance negative log-likelihood in float32. The front end moved to its own generated header (`andon_frontend.h`), so the device no longer needs the CNN's header to get its mel bank. Board run: `andon_bench.uf2`, captured with `andon.bench --port COM6`. Tables: `results/h5_gmm_bench_pico2.md`.
- **Result:**
  - On the board, both complete runs passed. Real-mic log-mel: worst 1.53e-05 dB (tolerance 0.001). Window mean: worst 1.14e-05 dB. Scores, relative error: worst 1.94e-06 from Python's window means (tolerance 1e-05) and 2.51e-06 end to end (tolerance 1e-04).
  - Time: 7.300 ms per GMM score, 1.684 ms of compute per 32 ms frame (the log-mel of every frame plus one score every 32 frames), under the 20 ms budget. Static RAM of the whole bench: 196,624 B.
  - Flash: the three fans' parameters take 402,480 B (`arm-none-eabi-nm`).
  - Before the board run, a dev-only check: the export's fit path reproduced H3's saved dev window scores bit for bit (both dev folds, seeds 0-2).
- **Decision:** H5 is done. Float32 rather than int8 Cholesky factors: it is the model that scored 100.00 on d3, so nothing needs re-scoring and no AUC is lost. All three fans go in one image, chosen at run time, so swapping fans in H6 and H7 needs no reflash. This puts the weights over Phase 4's written budget of 256 KB of int8 weights (`PLAN.md:93`), a budget set for the CNN. The 402 KB was accepted; one fan alone is 134,160 B, and the Pico 2 has 4 MB of flash.
- **Why:** a score takes 7.30 ms. That is far more than its 33,536 multiply-adds (4 components x (8,256 + 128)) suggest, probably because the 132 KB of one fan's factors are read from flash for every score (inferred, not profiled). It still fits: even unamortised, the slowest frame (1.74 ms of log-mel plus a 7.32 ms score) is under 20 ms. The bench was built from the working tree on top of `c4e4b9a` (the capture says `c4e4b9a-dirty`); its C sources are committed unchanged with this entry.

### 2026-11-10: Convolution kernel rewritten for speed; timed on the board 2026-11-14 (H5)
- **Tried:** a new `conv3x3` in `firmware/src/model.c`. The first version checked the padding on every tap inside the innermost loop. The new one gathers the 3x3 neighbourhoods of a strip of output positions once, as `q - zero` in int16 with 0 for padded taps (a 16 KB static buffer), then runs one dot product per output channel and position, written nine taps at a time. The output-channel loop stays outside the strip's positions, so one channel's weights (at most 576 bytes, in flash) are reused many times in a row.
- **Result:** bit-exact on the PC: the 13 firmware host tests pass, including every layer's int8 output and the head sums against the Python vectors. Cross-compiled for the Pico 2 (`-O3`), the inner loop is 3 instructions per multiply (two loads and one `smlabb`) plus 8 per nine taps, with no branches inside the nine. No timing was claimed until the board was available.
- **Result on the board (2026-11-14, built from `d4cb3c8`, 3 runs, `results/h5_bench_pico2.md`):** `self-test: PASS`, 0 of 24576 int8 inputs differ from Python, worst score error 2.48e-07. One CNN score takes 299.68 ms (the old kernel: 886.44 ms), so the total is 10.82 ms of compute per 32 ms frame on one core (the old kernel: 29.16 ms), under the 20 ms budget. Static RAM is 194560 B, up from 178176 B: the 16384 B difference is the kernel's gather buffer. One score is still 3.0 times the Phase 4 estimate of 98.32 ms.
- **Decision:** kept. The budget is met on one core, so the CNN does not have to move to core 1 for speed; whether it moves so the kill path never waits behind a 300 ms score is an H6 question.
- **Why:** plain C keeps one code path for the PC tests and the board, so the bit-exact check covers exactly what runs on the device. Integer sums don't depend on the order of addition and can't overflow int32 here, so reordering the loops can't change a result.

### 2026-11-07: Review fixes: fan off at boot, a stronger gate pull-down, and red before printing (H1)

### 2026-10-21: Own int8 reference instead of PyTorch quantization; budget estimated from MACs (Phase 4)
- **Tried:** `andon/quant.py` folds batch norm, stores weights as int8 with one scale per output channel, and activations as int8 with one scale and zero point per tensor (min/max of normal training data). Each layer's int32 sums are rescaled with a 31-bit fixed-point multiplier and a shift, rounding half up. The CNN is integer-only up to its last layer's sums; the logits and the score are float, since the Cortex-M33 has an FPU. The GMM stores only its precision Cholesky factors as int8 and scores in float. `andon/budget.py` counts MACs per score and converts them at an assumed 0.5 MAC per cycle at 150 MHz, spreading a window's cost over the frames between windows.
- **Decision:** kept (decided at the Phase 4 plan). The GMM tweaks deferred from Phase 3 were dropped: the CNN fits the budget, and H3 retrains on the real fan anyway.
- **Why:**
  - PyTorch's quantized kernels round in ways that aren't specified, so a C port could only approximate them. Our own reference defines every integer operation, so the C code can match it exactly on the test vectors.
  - Compute is an estimate until H5 measures it. One CNN window takes about 98 ms in one go, more than a 32 ms frame. Averaged over its 32 frames it is about 3 ms per frame, and the RP2350's second core can run it while the first keeps up with the audio.

### 2026-10-20: Andon simulator protocol (Phase 5)

### 2026-10-17: Match the Keras defaults the baseline relied on (Phase 1)
- **Tried:** reproduced what PyTorch does differently from Keras 2.1: Glorot-uniform weights and zero biases; batch norm momentum 0.99 (0.01 in PyTorch's convention) and epsilon 1e-3; Adam epsilon 1e-7; and `validation_split=0.1`, which holds out the last 10% of the unshuffled training windows (mostly the highest machine ID) rather than a random 10%. Like the baseline, one model per machine type is trained on the train clips of all its IDs, with no input normalization, and the last epoch is used (the held-out 10% only reports a loss).
- **Result:** see the reproduction entry above; no ablation of each detail was run.
- **Decision:** kept, all set in the config before the runs.
- **Why:** a few lines of config remove every obvious excuse if the numbers had missed; finding the cause of a gap afterwards would have cost far more training time.

### 2026-10-17: Fused Adam and 3 seeds in parallel to fit training on a laptop CPU (Phase 1)
- **Tried:** the default PyTorch Adam loops over the 36 parameter tensors one at a time: 4.8 ms per step against 0.9 ms for `fused=True`, which applies the same update in one kernel. With 8 threads a batch-512 step took about 10 ms, so one epoch on fan took 20 s and 18 runs one after another would have taken about 10 h. Three runs at 6 threads each ran at about 15 ms per step each, so about twice the throughput.
- **Result:** the full job (18 runs) finished in about 6.5 h overnight (ToyCar 84 min, slider 53 min per run).
- **Decision:** kept `fused=True`; `--threads` flag on `andon.train`; per-process temp files and a lock on `results_log.csv` so parallel seeds can't collide. Logs need `python -u`, otherwise piped output is buffered for hours.
- **Why:** keeps the CPU-only setup (no GPU, no data upload) without changing the training algorithm.

### 2026-10-17: Cache log-mel frames, stack windows per batch (Phase 1)
- **Tried:** the baseline builds every 640-value vector up front, about 3 GB of float32 per machine type. We cache only the 128-band frames (`data/cache/`, keyed by clip list and front-end settings) and stack 5-frame windows when each batch is built.
- **Result:** a test checks our stacking against the baseline's own loop, element by element, so the vectors are identical.
- **Decision:** kept.
- **Why:** 5x less memory, so three seeds fit in RAM at once.

### 2026-10-18: Results-log commit tags read "-dirty" because of the log itself (Phase 1)
- **Tried:** `git_commit()` marked a row `-dirty` whenever any tracked file had changes. `results_log.csv` is tracked, so after the first row every later row looked dirty.
- **Result:** 17 of the 18 Phase 1 rows read `e2db074-dirty`. During the runs `git status` showed `results/results_log.csv` as the only changed tracked file, so all 18 rows came from the code at `e2db074`. The later code diff touches only the summary print and this check, and re-scoring the saved fan and valve seed-0 checkpoints into a scratch log reproduced their logged AUC, pAUC and per-ID values exactly.
- **Decision:** rows left as written (the log is never edited by hand); the dirty check now ignores the log, with a test.
- **Why:** the tag exists to catch uncommitted code changes, not new results.

### 2026-10-17: Reflect padding at the clip edges, as in the baseline (Phase 0)
- **Tried:** the first version zero-padded the centered STFT frames, matching librosa 1.0's default. The baseline pinned librosa 0.6.0, whose `stft` defaults to `pad_mode='reflect'`.
- **Result:** zero padding moved only the first and last frame of each clip, by several dB; every other frame was unchanged (checked by `test_pad_mode_changes_only_the_edge_frames`). With reflect padding the librosa cross-check passes on every frame.
- **Decision:** kept `pad_mode="reflect"` as the `LogMelConfig` default; the librosa cross-check now passes `pad_mode="reflect"` explicitly.
- **Why:** Phase 1 has to reproduce the baseline exactly. The setting stays configurable because a streaming C front end has no "edge" to reflect.

### 2026-10-17: Download resumes even when the partial file is already complete (Phase 0)
- **Tried:** if a run stopped after the last byte but before the rename, the next run asked Zenodo for bytes past the end, got HTTP 416, and failed on every retry.
- **Decision:** kept: a 416 on a resume skips straight to the MD5 check, which deletes the file if it's bad. Tests cover both the 206 resume and the 416 case with a fake server.
- **Why:** the zips are 1 to 2 GB; a stuck download shouldn't need someone to delete files by hand.

### 2026-10-17: Cap numpy below 2.5 for Windows Smart App Control (Phase 0)
- **Tried:** `uv sync` resolved numpy 2.5.4; on the Windows dev machine Smart App Control refused to load its `_multiarray_umath` DLL, so nothing that imports numpy (torch, scipy, librosa) worked. numpy 2.3.5 and 2.4.6 load fine with the rest of the locked stack unchanged.
- **Decision:** kept `numpy>=2.0,<2.5`; locked to 2.4.6.
- **Why:** Smart App Control only trusts unsigned binaries once they have cloud reputation, which a brand-new release lacks. The cap can be lifted once a 2.5.x release loads on Windows.

### 2026-10-17: Log-mel in plain NumPy, cross-checked against librosa (Phase 0)
- **Tried:** wrote the baseline front end (1024-point FFT, hop 512, 128 Slaney mel bands, power 2, `10·log10(mel + eps)`) by hand instead of calling librosa.
- **Result:** unit tests on sine waves pass; a test compares it against librosa's `melspectrogram` within 0.01 dB.
- **Decision:** kept. librosa stays a dev-only dependency for that test.
- **Why:** the same steps are ported to C in Phase H4, so the Python reference must be simple and fully understood, and still match the baseline exactly.

### 2026-10-17: CPU-only PyTorch, stdlib WAV reader (Phase 0)
- **Tried:** pinned PyTorch to the CPU wheel index for all platforms; read WAVs with the standard `wave` module.
- **Decision:** kept.
- **Why:** keeps installs and CI small and identical on Windows and Linux; GPU training happens on Colab/Kaggle. DCASE clips are 16-bit mono PCM, so no native audio library is needed.
